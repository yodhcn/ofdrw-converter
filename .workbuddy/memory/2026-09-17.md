## 修复 CI 打包失败：`.git/` 被打进包 + 步骤 1 未传 `--max-size`

**现象**：GitHub Action `Repackage Dify Plugin`（linux-arm64）在
`1/5 构建常规包` 处失败：

```
ERROR failed to package plugin error="Plugin package size is too large.
Please ensure the uncompressed size is less than 52428800 bytes."
1. name: .git/objects/pack/pack-45044324....pack, size: 33272559 bytes
2. name: bin/runtime/lib/modules, size: 17264139 bytes
3. name: bin/ofdrw-text-cli.jar, size: 11581545 bytes
```

**根因（本地用同一份 CLI v0.6.10 实测复现）**：

1. `dify plugin package` **不会**自动跳过仓库元数据，而 `.difyignore` 里没有 `.git/`
   → 201 条 `.git/**` 条目进包。本地实测常规包 **324 项 / 解压 78.06 MB**（`.git` 占 ~33 MB）。
2. `build_base_package()` 打常规包时**没传 `--max-size`**，用的是客户端默认
   解压后 50 MB 上限；而自带 Java 运行时的包本来就贴着这条线（约 45 MB）。

**改动（4 个文件）**：

- `.difyignore`：新增 `.git/`、`.gitattributes`。
- `scripts/package_offline.py`：
  - 新增常量 `DEFAULT_MAX_SIZE_MB = 500`（对齐服务端放宽后的
    `PLUGIN_MAX_PACKAGE_SIZE=524288000` / `NGINX_CLIENT_MAX_BODY_SIZE=500M`）；
    新增 `ALLOWED_TOP_LEVEL` 顶层白名单（含 `.gitattributes`）。
  - 抽出 `list_package()` / `check_layout()`，供步骤 1 与步骤 5 共用。
  - 新增 `assert_clean_base_package()`：**打完常规包立刻体检**，命中 `.git/` 直接给出
    明确报错（"仓库历史会被打进交付包"），不再是一个含糊的「包太大」。
  - `build_base_package()` 增加 `max_size_mb` 参数并显式传 `--max-size`；
    `repack()` 自动值的下限从 50 提到 `DEFAULT_MAX_SIZE_MB`。
- `.github/workflows/repackage-plugin.yml`：仅加注释说明 `--max-size` 由脚本统一处理。
- `README.md`：体积约束表加"本项目"列；补第 3 条关键结论（`.git/` 必须排除，别删）；
  更新脚本流程与 `--max-size` 参数说明。

**验证**：
- 修复后同一 CLI 重新打包：**122 项 / 解压 45.34 MB / 压缩 31.94 MB**，`.git` 已不在包内。
- `assert_clean_base_package()` 反例测试：对含 `.git` 的旧包正确 `sys.exit` 并指出原因。
- `check_layout()` 正例（干净包 → `[]`）、反例（`.git/HEAD`、`build.log`、`.env`）均符合预期。
- `python scripts/validate.py --no-sample` 全绿；workflow YAML 可正常解析（14 步）。

**提交记录**：`7a323c8 fix(package): 排除 .git/，并为两步打包显式指定 --max-size`
（6 files changed, 182 insertions(+), 43 deletions(-)），已 push 到 `origin/main`。

## 追加：artifact 只含 SHA256SUMS.txt（glob 写错 + 静默漏传）

**现象**：用户跑完 arm64 workflow 后，下载的
`ofdrw-converter-offline-linux-arm64.zip` 里只有一个 `SHA256SUMS.txt`。

**根因**：`repackage-plugin.yml` 的 job env `ARTIFACT_PATH` 写的是
`dist/*-offline-${{ ... }}.difypkg` → 展开成 `dist/*-offline-**arm64**.difypkg`，
而真实产物是 `dist/ofdrw-converter-offline-**linux**-arm64.difypkg`（glob 少了 `linux-`）。
**关键：`upload-artifact` 在 pattern 只匹配部分文件时不报错**，
`if-no-files-found: error` 只在「一个都没匹配到」时触发 → 静默上传了剩下的那个校验和文件。

**改动**：去掉 `ARTIFACT_PATH`，新增 `Resolve package path` 步骤（`id: pkg`），
用 `ls -1 "dist/"*-offline-${PLATFORM}.difypkg` + `test -f` 解析真实路径写进 `$GITHUB_OUTPUT`；
`Generate checksum` / `Write job summary` / `Upload artifact` 统一引用
`steps.pkg.outputs.path|name`。命名一旦漂移，这一步 `ls` 就会失败、构建当场红。

**验证**：workflow YAML 可解析（15 步）；本地模拟旧 glob（匹配不到）与新解析逻辑（正确取到路径）。

**顺带确认**：这次 arm64 run 走到了 checksum/summary/upload，说明上一轮
`.git/` + `--max-size` 的修复**已经生效**（常规包构建通过）。

## 追加：安装后「无法启动 Java 进程，没有权限」（zip 不含权限位）

**现象**：插件在 Dify 上安装后调用工具报 `无法启动 Java 进程: [Errno 13] Permission denied`，
对应 `ofdrw_cli.py` 的 `except OSError` 分支。

**根因（实测证明）**：`dify plugin package` 写出的 zip 条目**完全没有权限信息** ——
本地重新打一个包检查，**122/122 条**都是 `create_system=0`(FAT)、`external_attr=0`（mode 0）。
所以与构建机是 Windows 还是 Linux 无关：解包后 `bin/runtime/bin/java` 就是普通只读文件，
exec 直接 EACCES。CLI 没有设置权限的入口。

**改动**：
- `scripts/package_offline.py`：新增 `EXEC_PREFIXES`/`EXEC_SUFFIXES`/`_mode_for()`、
  `entry_modes()`、`patch_unix_modes()`（重写 zip：`create_system=3` + 真实 mode，
  `bin/runtime/bin/*` 与 `*.so` = 0755，其余 0644），在 repack 之后调用；
  `verify_package()` 增加断言：包内 `bin/runtime/bin/java` 必须带可执行位。
- `ofdrw_cli.py`：新增 `_is_executable()`、`_ensure_executable()`、`_chmod_in_place()`、
  `_relocate_runtime()`，`resolve_java()` 对**自带**运行时（仅它）返回前确保可执行：
  已可执行 → 原路径；`chmod 0755` 成功 → 原路径；失败（只读挂载）→ 整棵运行时复制到
  `OFDRW_RUNTIME_CACHE` 或系统临时目录再补（整棵树是必须的，`bin/java` 靠 rpath
  `$ORIGIN/../lib` 找 `lib/server/libjvm.so`）。结果按路径缓存；加 `release` 文件存在性判断，
  避免误搬系统 JDK 目录。`check_environment()` 增加 `bundled_java_executable` /
  `java_executable` / `java_relocated` 诊断字段。
- `manifest.yaml`：版本 0.0.1 → **0.0.2**（便于区分必须重装的包）。
- `README.md`：关键结论补第 4 条、环境变量表补 `OFDRW_RUNTIME_CACHE`。

**验证**：`patch_unix_modes()` 在合成的包上断言 mode/create_system 正确、内容字节不变、幂等；
运行时三级策略用替换判定函数的方式逐条验证（已可执行不复制 / chmod 成功用原路径 /
chmod 失败复制整棵树含 release 与 libjvm.so / 无 release 时拒绝复制）；
`validate.py` 全量（含 12 个真实样例端到端）全部通过。

**结论**：必须重新打一次包并重装（0.0.2）。

## 追加：解析文本碎片化（「1 / - / 202 / 6」一字一行）

**现象**：用户反馈导出的纯文本里出现大量类似 `\n1\n- \n202\n6\n` 的零碎短行。

**根因（读 ofdrw 源码 + 本地复现确认）**：`TextExporter.export()` 把
`ContentExtractor.getPageContent()` 返回的每个字符串 `println` 一行，而后者是
「遍历 `TextObject` → 遍历 `TextCode` → `txtContentList.add(code.getContent())`」。
**切行完全不看坐标，一个 `TextCode` 就是一行。** 真实 OFD 大量采用
「一个字一个 `TextObject`」的排版，于是被拆成一堆单字行。

本地实测碎片化程度（`TextExporter` 行数 vs 按坐标重排行数）：

| 样本 | 对象数 | raw 行 | layout 行 |
| --- | --- | --- | --- |
| `999.ofd`（5 页发票） | 560 | 560 | **137** |
| `draw_param_ref.ofd`（5 页发票） | 870 | 873 | **146** |
| `SignScaleError.ofd`（发票） | 68 | 68 | **25** |
| `z.ofd`（OFD 标准节选） | 57 | 60 | **40** |

**几何规则（用自写的 Dump 工具从 12 个样本反推，逐条核对过）**：

- `TextObject.Boundary` = **页面坐标系**下的外接矩形（mm）；
- `TextCode.X/Y` = 相对对象原点的偏移，`X` 常为 0，`Y` ≈ 基线偏移；
- `TextCode.DeltaX/DeltaY` = **逐字步进**，累加值恰好等于文本宽度
  （`n.ofd` 实测 `50.04 = 4×5.57+4×2.77+5.57+2×2.77+5.57`），故可算出每个字的坐标，
  也能识别对象内部换行（`999.ofd` 里有 `dx=-17.4625, dy=3.175` 的回绕）；
- `CTM` 非单位矩阵 ⇒ 坐标系旋转/缩放 ⇒ **放弃逐字展开**，整块按 Boundary 定位；
  该情形下 `Size` 可能是畸高值（`文字横向-数科.ofd` 为 209mm），
  所以「字高」必须用 `Boundary` 高度而不是 `Size`。

**改动**：

- 新增 `jvm/.../LayoutTextExtractor.java`：展开逐字图元 → 按 y 聚类成行
  （容差 `0.35 × 中位字高`，下限 0.4mm）→ 行内按 x 排序 →
  间隙 > `0.3 × 字高` 补空格 → 按行输出；`extract()` 返回
  `lines / glyphCount / objectCount / fallbackObjectCount`。
- `Main.java`：`--mode layout|raw`（默认 layout），结果 JSON 加 `mode`、
  `glyphCount`、`unpositionedObjects`；版本 1.0.0 → 1.1.0（pom 同步）。
- `ofdrw_cli.py`：`convert_to_text(mode=)`、`normalize_mode()`（非法值回落 layout）、
  `_java_command()` 传 `--mode`，meta 增加 `mode`/`glyph_count`/`unpositioned_objects`。
- `tools/text_exporter.yaml`：新增 `mode`（`select`，默认 `layout`，`form: form`）。
- `manifest.yaml` / provider 描述：0.0.2 → **0.0.3**，措辞改为「按版面坐标还原阅读顺序」。
- `scripts/validate.py`：新增第 5 步**一致性回归** —— 每个样本同时跑两种模式，
  断言「非空白字符的多重集」完全相同且行数不变多。这是防静默丢字的硬约束。
- `README.md`：新增「为什么不能直接用 TextExporter」一节（含实测对比表）、
  更新架构图 / 目录结构 / 工具参数 / 已知限制（多栏排版仍会逐行合并）。

**验证**：12 个样本全部通过；一致性回归 `字符集完全一致，行数合计 1695 -> 421`；
非法 `--mode` 在 Java 侧退出码 2、在 Python 侧静默回落 layout；
试打包仍为 122 项 / 解压 45.37 MB / 合规顶层白名单；`validate.py` 五步全绿。

**遗留**：需要重新打 CI 包并重装 0.0.3。
